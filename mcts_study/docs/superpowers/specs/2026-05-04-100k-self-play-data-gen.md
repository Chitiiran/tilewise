# 100k Self-Play Data Generation — v3 Bootstrap Round 2

**Date:** 2026-05-04
**Status:** spec written, execution queued (waits for last-epoch tournament to finish)
**Owner:** automation; user pre-authorized launch

## Goal

Produce **100,000 self-play games** generated by `LookaheadMctsV3` (the same teacher used for the existing 10k v3 dataset), using identical game rules and identical evaluator config so the new data is a drop-in superset of the existing training corpus.

## Why now

1. The 9-cell × 20-epoch × {pass-1, pass-2} grid has converged to a clear ceiling: best PureGnn cell (h32_l2) gets **7.5%** vs Lookahead at 120 games. Most cells get 0%. The gap to LookaheadMctsV3 is enormous.
2. **The bottleneck is data, not architecture.** Across 9 architectures spanning 82k-632k params, no architecture meaningfully beat val_top1 ≈ 0.18-0.19 — the limit looks like *teacher noise floor / dataset size*, not capacity.
3. 10× more data is the cheapest way to push the ceiling. The teacher (LookaheadMctsV3 depth=500, base_sims=1000) is the same one that produced the existing 10k corpus, so the new data merges cleanly without distribution shift.
4. After this lands, the next training round can:
   - Train the existing 9-cell grid on the bigger 110k cache and see if the val_top1 ceiling moves.
   - Try the deferred wishlist (smaller archs h16/h8, dropout, weight-decay) on the bigger dataset.
   - Bootstrap a **GNN-rollout MCTS** (replace random rollouts with the trained value head) — see `docs/writeup.md:127` for the original outline.

## Spec for the 100k run

Same teacher, same rules, same schema, **10× the games + double the workers**.

### Command

```bash
TS=$(date +%Y-%m-%dT%H-%M)
nohup python -m catan_mcts run e9 \
  --out-root runs/v3/${TS}-e9_v3_data_gen_100k \
  --num-games 100000 \
  --base-sims 1000 \
  --lookahead-depth 500 \
  --seed-base 21000000 \
  --max-seconds 14400 \
  --vp-target 5 \
  --workers 16 \
  > runs/v3/${TS}-e9_v3_data_gen_100k.log 2>&1 &
```

Note: `e9_v3_data_gen` does not have `--bonuses` flag toggling — `bonuses=false` is the default and matches the existing 10k run.

### Flag rationale

| Flag | Value | Why |
|---|---|---|
| `--num-games` | 100000 | the headline target |
| `--base-sims` | 1000 | match existing 10k corpus |
| `--lookahead-depth` | 500 | match existing 10k corpus |
| `--seed-base` | 21000000 | disjoint from data-gen ranges 9M (default), 10M (e1-e7), 18M (training tournaments), 19M (pass-3) |
| `--max-seconds` | 14400 (4h) | per-worker time cap. Soft bound — workers exit cleanly when they hit it; salvage applies. The existing 10k run used 600s/worker but had only 1250 games each; here each worker handles 6250 games so we need ~10× the headroom. |
| `--workers` | 16 | the existing run used 8; this machine has more cores available. If this saturates → drop to 8 for the rerun. |
| `--vp-target` | 5 | match existing 10k corpus |

### Output layout

```
runs/v3/<TS>-e9_v3_data_gen_100k/
├── worker0/
│   ├── config.json
│   ├── done.txt                   (written when worker finishes; signal for resumability)
│   ├── games.v3-final.parquet     (one row per completed game)
│   └── moves.v3-final.parquet     (one row per (game, move_index) pair — the GNN training rows)
├── worker1/...
├── ...
└── worker15/...
```

### Resumability

`e9_v3_data_gen` resumes from existing `done.txt` markers by default. If a worker crashes mid-run, restart with the same command and only un-flagged seeds get regenerated. `--no-resume` would force a clean restart, but **DO NOT use it** for this run — preserve any partial progress.

## Cost estimate

The 10k run took ~1.3h wall-clock at 8 workers × 600s. Per-game time was therefore ~360 ms (actually wall-clock, not CPU; embarrassingly parallel).

For 100k games at 16 workers:
- If linear scaling holds: ~6.5h wall-clock
- If only 12-core scaling holds (Windows + WSL realities): ~8h
- If 8-core scaling and we keep 16 workers: ~13h
- **Plan: budget 8-13h, time-cap each worker at 4h (--max-seconds 14400) so a stuck worker can't poison the run**

## Salvage policy

Per `feedback_salvage_compute_and_time` and `feedback_never_rm_rf_training_output`:

- **Per-worker parquet flush:** e9_v3_data_gen flushes `games.v3-final.parquet` only at worker exit. If a worker crashes mid-run with no flush, those games are lost. Mitigation: per-worker time cap (4h) keeps loss bounded. Future improvement: incremental flush every N games.
- **If killed for any reason:** preserve the output dir. Move to `.bak/` if disk space is needed; do NOT `rm -rf`.
- **If a single worker fails:** the others continue independently. Re-run with the same command afterward; resume picks up only the seed ranges that don't have `done.txt`.
