## PRE-LAUNCH VERDICT — AZ self-play 6-day run

### 1. MUST-FIX BEFORE LAUNCH (silent corruption, wasted run, or wrong verdict)

**M1. Seed-base is identical every iteration → diversity collapse at `games_per_iter` boards (concurrency-resource, HIGH).** Every iter replays the same ~1000 board seeds; the run can only ever memorize a fixed board set, defeating the entire 6-day point and explaining the HOLD streaks. This silently invalidates the whole run's premise.
*Fix:* `daily.py:117` — add the iteration term: `sb = 31_000_000 + gen_iter * 10_000_000 + i * 1_000_000` (gen_iter is already in scope, passed at daily.py:106).

**M2. PUBLISH double-applies on mid-block crash → permanent ladder Elo/games corruption + duplicate journal rows (crash-resume, HIGH).** `register_candidate` and `record_arena` are non-idempotent and guarded by a single trailing marker; a crash after `record_arena._save()` re-applies the Elo delta and games count on resume. This corrupts the promotion-gating signal and web difficulty tiers persistently — a wrong verdict, undetected. The code's own comment documents the prior "240 games + duplicate promote" incident.
*Fix:* `loop.py:159` — write `PUBLISH.done` as a *claim at the start* of the block (or make `record_arena`/`register_candidate` idempotent via an arena/iter key); the trailing-only marker is the bug.

**M3. Arena `gather(return_exceptions=False)` → a deterministic engine/MCTS exception is a permanent gate poison-pill (crash-resume, MED — but blocks the run indefinitely).** A deterministically-raising seat/seed is never written to `done`, gets replanned every restart, `run_arena` never returns, ARENA never marks done → the iteration is wedged forever with no human present. Same class: **arena `results.jsonl` resume has no parse-guard (HIGH)** — a torn final line raises `JSONDecodeError` and poison-pills the iteration identically.
*Fix:* `arena.py:267` set `return_exceptions=True` + log failures (mirror self_play_async); `arena.py:210` wrap `json.loads(line)` in `try/except JSONDecodeError: continue` (mirror analytics.py:97-100, which already does exactly this on the same file).

**M4. Partial-worker death is silent → trains every iteration on a fraction of intended data for 6 days (observability + concurrency, HIGH).** `p.wait()` discards returncodes; the only guard is aggregate `produced==0`. On the shared 4GB card, a CUDA-OOM race that kills 3 of 7 workers leaves the iteration training on ~30 games against a 1000 quota, with no flag — and a cleanly-completed undersized iter is *not* repaired by deficit-resume. Compounded by **VRAM overcommit: `7×535MB` ignores model+activation footprint (HIGH)**, which makes partial OOM-death the *expected* failure mode, not a rare one.
*Fix:* `daily.py:133` — after `p.wait()`, assert each `p.returncode==0` AND `produced >= games_per_iter * 0.8`, else raise (fail loud + resume); and lower `worker_procs_max` or raise `per_proc_vram_mb` in `config.py:65` so the planned fit leaves headroom for weights+activations (e.g. set `per_proc_vram_mb≈800`).

### 2. SHOULD-FIX (degrades but survivable)

- **Orphaned self-play (no meta.json until all procs exit) — HIGH-rated but bounded:** re-runs hours of self-play per mid-selfplay restart and orphans get archived away. Fix: write per-proc `meta.json` immediately after each `Popen` (daily.py:133) — it's static. *Strongly recommended given near-certain mid-selfplay crashes over 6 days, but it only wastes compute, doesn't corrupt.*
- **`shutil.copyfile` of champion .pt not atomic (MED):** rare durability hole can wedge the champion. Fix: copy to `.tmp` + `os.replace` + a `torch.load` sanity check before `register_candidate` (loop.py:164).
- **`journal.csv` full-rewrite not atomic (MED):** a mid-rewrite crash resets the stagnation counter → run won't auto-stop. Fix: tmp+`os.replace` mirroring `stage()`/`_save()` (status.py:43). 2-line fix.
- **No `p.wait()` timeout → one hung worker stalls iter up to 6h (MED):** Fix: `p.wait(timeout=max_seconds+margin)` then kill+log.
- **Self-play has no heartbeat → dashboard reads alive=True for up to 8h on a hang (HIGH-rated observability):** purely observability; fix by touching `daily_state.json` mtime inside the wait, or poll parquet mtime. Without M4's loud guard this matters more.
- **Parent death leaks orphan GPU workers up to ~6h (MED):** Fix: `start_new_session=True` + atexit/SIGTERM handler that kills the group (daily.py:132).
- **`count_games` double-counts `_remainder` + per-seed shards (LOW) / phantom winner=-1 shards (LOW):** quota undershoot. Cheap: `count_games` should `drop_duplicates(subset="seed")` and filter `winner!=-1` (buffer.py:22).

### 3. ACCEPTABLE (known, monitor on dashboard)

- **100%-timeout arena makes winrate a VP-leader proxy (MED, gate-correctness):** intentional design (tests enshrine it); VP-leader correlates with winner and draw/decisive guards catch the degenerate case. Accept, but add a logged decisive-by-timeout fraction and watch it. *Watch for promotion of pure early-VP-rush champions.*
- **No detector for steady-100%-timeout / `new_games < quota` (MED/LOW observability):** binary `==0` cliffs. Accept with M4 in place (M4's `<0.8*quota` assert covers the dangerous half).
- **Non-atomic two-file shard write / atexit compaction torn parquet (LOW):** self-healing via per-seed shards + done.txt resume; dataset dedups. Monitor for a training-time `pq.read_table` crash (the one residual: a truncated compacted parquet at a glob-matched name — manual `rm` recovers).
- **Timed-out async games leave no `skipped.csv` (MED→selection bias):** the long resource-starvation games are dropped silently; tolerable for this run, note the bias.
- **`daily.lock` PID-reuse / non-atomic acquisition (LOW):** worst case is one skipped day on daily cron; recoverable.
- **`max_iters_reached` flips dashboard to alive=False after 30 min (MED cosmetic):** looks like a crash but stage word is on-screen; one-line fix optional.

### 4. RECOMMENDATION

**NO-GO until M1–M4 are fixed; GO once they are.** M1 alone makes the run scientifically worthless, M2 silently corrupts the promotion verdict, M3 wedges the gate with no human present, and M4 trains on a fraction of the data — these are the four "silently corrupts data / wastes the run / wrong verdict" categories. The remaining HIGH items (orphan self-play, self-play heartbeat) are efficiency/observability and survivable for a first unattended run; ship them in the same patch if cheap, but they are not launch-blockers.

### [LOW] daily.lock is a plain PID file with a kill -0 check -> PID reuse over a 6-day cron cadence can wrongly mark a run active and abort, or two runs can race the lock
- **Surface:** concurrency-resource
- **Location:** scripts/run_az_day.sh:13
- **Scenario:** The lock test is `[ -f LOCK ] && kill -0 $(cat LOCK)`. So if the stored PID is reused by an unrelated process, kill -0 succeeds and line 15 (`exit 1, "another run is active"`) wrongly aborts the day. CONFIRMED. The stale-lock precondition is also real: line 17 `trap 'rm -f "$LOCK"' EXIT` does NOT fire on SIGKILL(9), so a hard-killed run leaves the lock behind for a future PID to collide with. CONFIRMED. WHY low not med: the worst realistic outcome of the PID-reuse case is SKIPPING ONE DAY (clean exit 1 with a clear message); next day's invocation faces a fresh PID landscape and recovers. The double-launch/VRAM-OOM path requires a manual concurrent invocation, not the daily cron. daily_state.json + per-game flush mean a skipped day loses zero training state. Defect is genuinely present (no atomic flock, no PID-identity check) but consequence is a recoverable missed day, not a corrupted or doubled run. Concrete fix if desired: use `flock` or `mkdir` for atomic acquisition, store PID+start-time, and verify the locked PID's cmdline matches 'catan_az.daily' before honoring the lock.
