# RCA: the fresh-ratio fix failed to prevent stale data — how it was missed

**Date:** 2026-06-14
**Severity:** the headline AZ-improvement mechanism was silently not running for
iters 4–5 (0 new games), masked as "HOLDs".

## The bug, proven

`fresh_deficit` (buffer.py) decides how many NEW self-play games an iteration
must generate so current-champion games are ≥ `fresh_ratio` (0.70) of the window.

```python
for d in iter_dirs_newest_first:
    m = _read_meta(d)                      # {"rules_id":..., "champion":...}
    if m.get("champion") == champion and m.get("rules_id") == rules_id:
        fresh += count_games(d)            # <-- counts ALL games tagged with
                                           #     the current champion's NAME
target = ceil(fresh_ratio * window_games)
return max(0, target - fresh)
```

Self-play dirs are tagged `{"rules_id": "v3-full", "champion": "az_iter_1"}` —
**no iteration number, no generation/timestamp.** So "fresh" means "any game
ever generated by a net named az_iter_1," NOT "games generated *this iteration*
by the current policy."

**What happened:** iter-3 generated 810 games tagged `champion=az_iter_1`. The
champion stayed az_iter_1 (iters 2–5 all HOLD). When iter-4 ran:
`fresh = 810 ≥ target ceil(0.70 × 1200) = 840`? — close, and with the resume
top-ups it cleared the bar → **deficit = 0 → generated 0 new games → trained on
iter-3's pool.** Same for iter-5. Verified: iter_4/iter_5 SELFPLAY.done list
identical 21 dirs, all `/iter_3/`.

## THE ROOT CAUSE (definition error, not a logic bug)

The fix conflated two different meanings of "fresh":
- **Intended:** "generated by the *current iteration's* champion-as-of-now,"
  i.e. recent experience from the policy we're training against.
- **Implemented:** "tagged with the champion's *name*."

These coincide ONLY while the champion changes every iteration. The moment the
champion is **sticky** (no promotion for several iters — the exact regime AZ
spends most of its time in once it's decent), the name-tag stops meaning
"recent" and old games masquerade as fresh forever. The ratio fix prevented
*window dilution by a DIFFERENT champion's games* (iter-2's failure) but not
*staleness by the SAME champion's old games*.

## How it was missed — five contributing causes

1. **Wrong test coverage.** `test_az_fresh_ratio.py` tested exactly the
   coinciding case (old=cell6, new=az_iter_1) — different champions. There was
   **no test for "same champion across iterations"**, which is precisely where
   the definitions diverge. The fix was tested against the failure it was
   designed for, not the new failure it introduced.

2. **The metadata can't express "recent."** `meta.json` tags champion + rules
   but not iteration/timestamp, so even a correct deficit calc had no field to
   distinguish iter-3's az_iter_1 games from iter-5's. The data model was
   missing the dimension the logic needed.

3. **No observability on the load-bearing number.** Nothing logged
   `new_games this iter` or `deficit`. The journal logged `window_dirs` (which
   GREW, 13→25, looking healthy) but not "how many of these are NEW." A growing
   window masked zero fresh generation. (Fixed today: PROGRESS.md new_games
   column + STALE flag.)

4. **The symptom mimicked a plausible real result.** "HOLD at ~50% winrate"
   reads as "improving on a good champion is hard" — a believable AZ story — so
   it didn't trigger suspicion. The bug hid behind a reasonable-looking outcome.
   (I even narrated that story before checking the data — see cause 5.)

5. **Operator (me) asserted instead of verifying.** I claimed "fresh-ratio fixes
   dilution" and "let it run" without opening SELFPLAY.done to confirm new data
   was actually being generated. The tracking existed; I didn't read it. The
   user caught it by asking "are we making new data?"

## Fixes

### Now (observability — done)
PROGRESS.md (commit 22632b9): per-iteration `new_games` + `trained_on` with a
STALE flag. Makes cause 3 impossible to miss going forward.

### Required (the actual bug — to implement)
Make "fresh" mean "recent," not "same name." Options:
- **A. Tag generation iteration.** Add `"gen_iter": N` to meta.json; `fresh_deficit`
  counts only dirs with `gen_iter >= iter_n - K` (or `== iter_n`). Cleanest;
  needs the metadata field (cause 2).
- **B. Always generate a floor.** `min_fresh_games_per_iter` (e.g. ≥200 new
  games every iteration regardless of deficit). Simple, guarantees new
  experience, but mixes "freshness policy" with "minimum data."
- **C. Self-play from the candidate, not the champion.** Even a held candidate
  is a *different* net → its games are genuinely new experience → the pool
  evolves each iteration. Most AZ-faithful; changes what we self-play with.

### Required (the test gap — cause 1)
A test: "same champion across two iterations → the second still generates new
games (or the chosen policy's intended behavior)." This is the test that would
have caught it.

## Observability principle (generalize)
Every load-bearing decision number (deficit, new_games, what-trained-on) must be
**logged where a human sees it**, not just computed internally. The window grew
while fresh-generation was zero — a derived metric looked healthy while the
load-bearing one was broken. Surface the load-bearing one.
